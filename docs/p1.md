| `<login>SW` | K3s agent (worker) | `192.168.56.111` | 1 CPU, 1024 MB |

O Vagrantfile declara a origem em `config.vm.box_url`, que aponta para o [release `box-debian-13.7.0`](https://github.com/northwindstudios/inception-of-things/releases/tag/box-debian-13.7.0) deste repositório (~420 MB), com `box_download_checksum` SHA256. ## Rede privada

Cada VM tem duas interfaces:

| Interface | Tipo | Endereço |
|-----------|------|----------|
| `enp0s3` | NAT do VirtualBox (saída para a internet) | `10.0.2.15` |
| `enp0s8` | `private_network`, dedicada ao cluster | `192.168.56.110` (server) / `192.168.56.111` (worker) |

Verificação (com as VMs de pé):

```bash
vagrant ssh <login>S  -c 'ip -br -4 a; ping -c 3 192.168.56.111'
vagrant ssh <login>SW -c 'ip -br -4 a; ping -c 3 192.168.56.110'
```

Esperado: `enp0s3` com `10.0.2.15`, `enp0s8` com o IP da própria VM e 0% de perda no ping.

## SSH sem senha

O subject pede `vagrant ssh <login>S` e `vagrant ssh <login>SW` sem senha. O `vagrant ssh` usa chave:

- A box traz a chave insegura pública do Vagrant. No primeiro boot, o `insert_key` padrão a troca por uma chave única por VM. A chave privada fica em `p1/.vagrant/machines/<vm>/virtualbox/private_key`, ignorada pelo git. Nenhuma chave nem senha é commitada.
- [`scripts/ssh.sh`](../p1/scripts/ssh.sh) roda em todas as VMs, antes dos scripts de cada papel, e fecha o resto: desliga `PasswordAuthentication` e `KbdInteractiveAuthentication`, bloqueia o login de root e trava a senha do `vagrant`. A senha `vagrant` do preseed só serve para o Packer entrar durante o build da box. O sudo sem senha do `vagrant` continua.
- O arquivo de configuração é `/etc/ssh/sshd_config.d/10-iot.conf`. O prefixo `10-` faz o sshd ler esse arquivo antes do `99-vagrant.conf`, porque vale o primeiro valor lido.

Verificação:

```bash
vagrant ssh <login>S  -c 'hostname'     # abre sem pedir senha
vagrant ssh <login>SW -c 'hostname'
vagrant ssh <login>S -c 'sudo sshd -T | grep -E "^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin) "; sudo passwd -S vagrant'
# no, no, no e status L (senha travada)
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password vagrant@192.168.56.110   # Permission denied (publickey)
```

## Token do cluster

O agent do K3s precisa do token do servidor para entrar no cluster, e os dois scripts rodam em VMs diferentes. O token chega ao worker sem passo manual e sem ir para o repositório:

- O [`p1/Vagrantfile`](../p1/Vagrantfile) gera um token aleatório (`SecureRandom.hex(32)`) na primeira vez que `vagrant up`, `provision` ou `reload` roda, e o grava em `p1/.vagrant/k3s-token` com permissão `600`. A pasta `.vagrant/` é ignorada pelo git, então o arquivo nunca aparece no `git status`. Comandos como `vagrant status` e `vagrant ssh` não criam o arquivo.
- O mesmo valor vai para as duas máquinas na variável `K3S_TOKEN`, e o Vagrant o mascara na saída (`config.vagrant.sensitive`).
- [`scripts/server.sh`](../p1/scripts/server.sh) o grava como `token:` em `/etc/rancher/k3s/config.yaml`, que fica com permissão `600`, e o K3s usa esse valor como token do cluster. Por isso `/var/lib/rancher/k3s/server/node-token` e o token recebido pelo worker são o mesmo segredo.
- [`scripts/worker.sh`](../p1/scripts/worker.sh) o grava em `/etc/rancher/k3s/join-token` (`600`, dono root). O agent lê esse arquivo pela opção `token-file`.
- `vagrant destroy` do servidor apaga `p1/.vagrant/k3s-token`: um servidor novo é um cluster novo e ganha um token novo.

Não usamos a pasta sincronizada `/vagrant` para copiar o token, porque o Vagrantfile a desativa (`synced_folder ... disabled: true`) e porque uma pasta compartilhada colocaria o segredo dentro do diretório do projeto, sem garantir a permissão `600`. A box é construída sem guest additions (`guest_additions_mode = "disable"`); o aviso "Guest Additions Version: 6.0.0" do Vagrant parece vir do driver `vboxguest` embutido no kernel e não atrapalha nada aqui.

VMs criadas antes desta mudança não têm o token no `config.yaml`. Recrie o ambiente com `vagrant destroy -f && vagrant up`.

Verificação (compara só os hashes, sem imprimir o token):

```bash
vagrant ssh <login>SW -c 'sudo stat -c "%a %U" /etc/rancher/k3s/join-token'     # 600 root
vagrant ssh <login>SW -c 'sudo sha256sum /etc/rancher/k3s/join-token'
vagrant ssh <login>S  -c 'sudo stat -c %a /etc/rancher/k3s/config.yaml'          # 600
git check-ignore -v p1/.vagrant/k3s-token                                        # coberto por .vagrant/
```

## Agent do K3s

[`scripts/worker.sh`](../p1/scripts/worker.sh) instala o K3s em modo agent em `<login>SW` e o junta ao servidor, no mesmo desenho do `server.sh`:

- A configuração vai em `/etc/rancher/k3s/config.yaml` (`600`): `server: https://192.168.56.110:6443`, `token-file: /etc/rancher/k3s/join-token` (o token da seção anterior, que não é repetido no config), `node-ip` e `flannel-iface`. A interface é descoberta pelo IP, como no servidor.
- O Vagrantfile passa `SERVER_IP`, derivado de `MACHINES`, em vez de repetir o IP no script.
- Antes de instalar, o script espera a API do servidor responder em `https://192.168.56.110:6443/cacerts`, por até 180 s, o que evita a corrida no `vagrant up`. A porta 6443 está aberta: a box não tem firewall.
- Instala a mesma versão fixada do K3s (`K3S_VERSION`) só se ela faltar ou mudar. O serviço só é reiniciado quando o `config.yaml` muda, então `vagrant provision` não derruba o agent.
- O instalador roda com `INSTALL_K3S_SKIP_START=true` e o serviço é iniciado com `systemctl start --no-block`. A unit `k3s-agent` é `Type=notify`, então um `start` normal bloqueia até o agent entrar, e um agent que não entra deixaria o `vagrant up` preso. O script espera o `k3s-agent` ficar `active` por até 180 s e, se não ficar, imprime o `systemctl status` e sai com erro.
- O nó aparece em minúsculas (`fnascimesw`) e com role `<none>`, que é como o K3s mostra um agent. O `kubectl` só funciona no servidor, porque o worker não tem kubeconfig.

### Memória do servidor

O servidor tem **2048 MB** e o worker 1024 MB. Com 1024 MB o servidor travou quando o worker entrou: chegou a cerca de 950 MB usados de 967 MB, com ~16 MB disponíveis e 24% de pressão de memória (a VM não tem swap), e o `sshd` parou de entregar o banner. Mesmo sozinho, com o K3s padrão, ele já ficava com só 70 a 110 MB livres. Desativar traefik, metrics-server e servicelb não resolveu. Com 2048 MB e os dois nós `Ready`, o servidor usa cerca de 1,3 GB, tem ~690 MB disponíveis e nenhuma pressão de memória; o worker usa cerca de 330 MB.

Verificação:

```bash
vagrant ssh <login>S  -c 'sudo kubectl get nodes -o wide'      # os dois Ready; o worker com role <none>
vagrant ssh <login>SW -c 'systemctl is-active k3s-agent'       # active
vagrant ssh <login>SW -c 'curl -ksf -o /dev/null -w "%{http_code}\n" https://192.168.56.110:6443/cacerts'   # 200
vagrant ssh <login>SW -c 'sudo stat -c "%a %U" /etc/rancher/k3s/config.yaml'   # 600 root
```

## Por que construímos a box com Packer

O subject exige que o Vagrantfile diga de onde vem a box (`box_url`), com uma imagem publicada pela própria distribuição ou uma box construída por nós, porque o registry da HashiCorp não é garantido depois de 2026.

- O Debian não publica `.box` próprio. A `debian/trixie64` do Vagrant Cloud é mantida pelo time do Debian, mas só tem o provider **libvirt**, não VirtualBox.
- O Rocky Linux 10 publica box VirtualBox oficial, mas exige CPU **x86-64-v3** (AVX2, BMI, FMA). No homelab anterior (Celeron J1800, 2013) a VM travava no boot com `gurumeditation`. O Debian roda em qualquer x86-64.
- Então construímos a box do Debian 13 a partir da **ISO oficial** (netinst, com checksum SHA256 fixado).

### Como a box é construída

| Arquivo | Função |
|---------|--------|
| [`p1/scripts/build.sh`](../p1/scripts/build.sh) | Roda `packer init` e `packer build`; remove do cache do Vagrant qualquer box `debian13` antiga. |
| [`p1/confs/packer/debian-13.pkr.hcl`](../p1/confs/packer/debian-13.pkr.hcl) | Template do Packer: ISO, recursos da VM de build, `boot_command`, pós-processador `vagrant`. |
| [`p1/confs/packer/http/preseed.cfg`](../p1/confs/packer/http/preseed.cfg) | Respostas do instalador do Debian (instalação sem intervenção, usuário `vagrant`, uma partição ext4 **sem swap**). |
| [`p1/confs/packer/provision.sh`](../p1/confs/packer/provision.sh) | Dentro da VM de build: chave SSH do Vagrant, `UseDNS no`, limpeza e **zerar o espaço livre** (a box cai de ~830 MB para ~420 MB). |

Sem swap porque o kubelet do K3s se recusa a subir com swap ligada por padrão. A linha `dd: error writing '/EMPTY': No space left on device` no log do build é esperada: é o zero-fill chegando ao fim do disco.

O resultado é `p1/boxes/debian-13-virtualbox.box` (ignorado pelo git, como todo `*.box`).

- O build baixa a ISO (~790 MB), instala o Debian pela rede e gera uma box de ~420 MB. No homelab anterior (Celeron J1800) levou **cerca de 40 minutos**; o tempo no atual não foi medido.
- **Só é necessário rodar o build para mudar a box** (template, preseed, `provision.sh` ou ISO). Quem só quer subir as VMs usa a box publicada no release.
- A URL da ISO usa `.../iso-cd/` (`current`), que guarda só a versão pontual mais recente. Quando o Debian lançar a próxima (13.8, por exemplo), o download falha: atualize `iso_url` e `iso_sha256` no template (os checksums estão no `SHA256SUMS` da mesma pasta).

### Publicando uma box nova

Depois de reconstruir e validar a box localmente:

```bash
BOX_URL="file://$PWD/boxes/debian-13-virtualbox.box" vagrant up   # testa a box local (sem checksum)
shasum -a 256 boxes/debian-13-virtualbox.box
gh release create box-debian-<versão> boxes/debian-13-virtualbox.box --title "..." --notes "..."
```

Depois atualize `BOX_URL` e `BOX_SHA256` no `Vagrantfile`. Use um tag novo por versão, em vez de sobrescrever o arquivo de um release existente, para não quebrar quem já fixou o checksum antigo. Releases de arquivos grandes não têm custo no GitHub (limite de 2 GiB por arquivo).

## Vagrant não é Ansible

O Vagrant **cria** VMs num hypervisor local e depois as provisiona. Ele não configura servidores que já existem (isso é Ansible). Por isso o p1 tem que rodar numa máquina com hypervisor; VPS existentes só servem como **host** do Vagrant, e precisam de virtualização aninhada e recursos para as duas VMs (3 GB no total).

## Rodando no Ubuntu (homelab)

Host de teste atual: Ubuntu 25.10, bare metal, Intel Core i5-10210U (4 núcleos, 8 threads) com VT-x, 7 GiB de RAM e 4 GiB de swap no host, Secure Boot desligado (o módulo do VirtualBox não carrega com ele ativo sem assinatura). ```bash

  | sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt update && sudo apt install -y vagrant virtualbox
sudo apt install -y packer   # só se for reconstruir a box
vagrant --version; VBoxManage --version

No Ubuntu 25.10 (codename `questing`) o repositório da HashiCorp não tem esse codename, e o `apt update` acusa que o `InRelease` não está assinado. No homelab atual o VirtualBox vem do repositório do Ubuntu (`sudo apt install virtualbox`, pacote 7.2.2) e o Vagrant do Linuxbrew (`brew install vagrant`). O usuário precisa estar no grupo `vboxusers`.

Versões usadas no homelab atual: Vagrant 2.4.9, VirtualBox 7.2.2. No anterior: Vagrant 2.4.9, Packer 1.16.2, VirtualBox 7.0.16.

## Troubleshooting

### O `vagrant up` falha ao baixar a box ou com erro de checksum

Confira se o release `box-debian-13.7.0` ainda existe e se `BOX_SHA256` no `Vagrantfile` é o SHA256 do arquivo anexado. Para usar uma box construída localmente: `BOX_URL="file://$PWD/boxes/debian-13-virtualbox.box" vagrant up`.

Se uma box `debian13` antiga ficou no cache do Vagrant, remova com `vagrant box remove --all debian13`.

### O servidor trava quando o worker entra no cluster

Sintomas: o `vagrant up` do worker falha com `k3s agent not ready after 180s`, o `sshd` do servidor aceita a conexão mas não entrega o banner (`Connection timed out during banner exchange`), o `journalctl` do servidor mostra `Under memory pressure, flushing caches` e o `systemd-journald` do boot anterior acusa o mesmo. A causa é memória: o servidor precisa de mais de 1 GB. Confira que o `memory: 2048` do servidor no `MACHINES` do Vagrantfile está aplicado e recrie as VMs (`vagrant destroy -f && vagrant up`).

### Recriei só o worker e ele não entra (`Node password rejected`)

Sintomas: depois de `vagrant destroy -f <login>SW && vagrant up <login>SW`, o `up` falha com `k3s agent not ready after 180s`, o `journalctl -u k3s-agent` do worker mostra `Node password rejected, duplicate hostname`, e o servidor ainda lista o nó antigo como `NotReady`. O servidor guarda uma senha por nome de nó, e a VM nova gera outra senha com o mesmo nome. O ciclo completo (`vagrant destroy -f && vagrant up`) não tem esse problema, porque recria o servidor também.

Correção, no servidor, e depois reprovisione o worker:

```bash
vagrant ssh <login>S -c 'sudo kubectl delete node <login>sw'
vagrant ssh <login>S -c 'sudo kubectl -n kube-system delete secret <login>sw.node-password.k3s'   # só se o segredo ainda existir
vagrant provision <login>SW
```

O nome do nó é o `<login>SW` em minúsculas (`fnascimesw`). Nos testes, o agent entrou e o nó ficou `Ready` logo depois do `provision`.

### O build do Packer falha ao baixar a ISO

O Debian moveu a ISO para o arquivo quando saiu uma nova versão pontual. Atualize `iso_url` e `iso_sha256` em `confs/packer/debian-13.pkr.hcl`.

### `The private key ... must be owned by the user running Vagrant`

Alguém rodou `sudo vagrant up` e o `.vagrant/` ficou com dono `root`. Para corrigir:

```bash
sudo vagrant destroy -f
sudo rm -rf .vagrant
vagrant up   # sem sudo
```

### VirtualBox não sobe VM (`vboxdrv` não carregado, `VERR_VMX_IN_VMX_ROOT_MODE`)

- Com Secure Boot ligado, o módulo `vboxdrv` precisa ser assinado e a chave registrada via `mokutil` (o `apt` pede uma senha de MOK; confirme no próximo boot). Cheque com `mokutil --sb-state`.
- O KVM carregado (`kvm_intel` / `kvm_amd`) toma o VT-x. Descarregue com `sudo modprobe -r kvm_intel kvm` (ou `kvm_amd`) e, para ficar permanente, faça blacklist ou use `kvm.enable_virt_at_load=0` no GRUB.
- Se o Vagrant não reconhecer a versão do VirtualBox do Ubuntu, instale o VirtualBox do repositório da Oracle.

### VM em `gurumeditation` logo no boot

Em geral é a CPU do host sem as instruções que a imagem exige (foi o caso do Rocky Linux 10 no homelab). Confira os flags com `grep -m1 flags /proc/cpuinfo` e veja o `VBox.log` em `~/VirtualBox VMs/<vm>/Logs/`.
